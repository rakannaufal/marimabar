# Backend Teman Mabar MVP

## Setup

1. Buat proyek Supabase development terpisah; aktifkan verifikasi email di Auth. Atur Site URL dan redirect login/reset sesuai origin aplikasi. Jangan taruh `service_role` di browser; hanya URL proyek dan publishable/anon key yang boleh dipakai frontend.
2. Terapkan semua file `supabase/migrations/*.sql` menurut urutan nama lewat Supabase CLI (`supabase db push`) atau SQL Editor sebagai pemilik database. Jalankan `supabase/seed.sql` sesudah migrasi; seed hanya katalog empat game, tanpa akun/password.
3. Bootstrap admin setelah akun Auth pertama dibuat dan email diverifikasi: di SQL Editor dengan akses pemilik database, jalankan `update public.user_roles set role='admin', granted_by='<ADMIN_UUID>'::uuid, granted_at=now() where user_id='<ADMIN_UUID>'::uuid;`. Trigger `role_audit_change` mencatat perubahan. Jangan buat endpoint klien untuk perubahan peran.
4. Profil Auth dibuat dengan deklarasi usia 18+ dari metadata registrasi `adult_declared=true` yang dikirim form dan dicatat sekali oleh trigger. Ini **deklarasi mandiri**, bukan bukti usia; tinjau age assurance sebelum produksi. Tidak ada endpoint klien yang dapat mengubah `adult_declared_at`.
5. Untuk pengujian: `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f tests/sql/mvp.sql` pada database Supabase development yang sudah dimigrasi dan di-seed. Tes memakai transaksi rollback dan empat pengguna Auth sintetis; jalankan hanya sebagai role pemilik database. Tidak pernah jalankan pada produksi.

## Kontrak frontend

- `search_game_profiles(p_game_slug text, p_rank text default null, p_roles text[] default null, p_mode text default null, p_region text default null, p_ready boolean default null, p_limit int default 20, p_offset int default 0)` mengembalikan set DTO `id uuid, user_id uuid, game_id uuid, game_name text, display_name text, avatar_url text, ign text, rank text, role text, region text, ready boolean, updated_at timestamptz, bio text`.
- `public_profile_detail(p_id uuid)` mengembalikan 0 atau 1 baris DTO dengan kolom yang sama. `p_id` ialah **game_profiles.id**, bukan user ID. `rank`, `role`, `region` ialah label katalog. Filter memakai **code** katalog. Paging offset 0–5000, limit 1–50; urutan kesegaran, waktu, ID stabil. Dalam kategori `p_roles` berlaku OR; antarfilter AND. Rank game bermode harus disertai `p_mode` untuk perbandingan tepat.
- Baca pemilik: `profiles`, `game_profiles`, `game_profile_options`, `availability_slots`; pengguna lain hanya melalui RPC publik. Mutasi lintas pihak: `create_invite(recipient,game,message)`, `respond_invite(id,accept)`, `cancel_invite(id)`, `send_message(conversation,body)`, `share_game_id(conversation,game_profile)`, `revoke_game_id_share(id)`, `read_shared_game_id(conversation,owner)`, `create_report(reported,category,description,target_type,target_id)`, `apply_moderation_action(subject,action,reason,report)`; nama argumen SQL semuanya berawalan `p_`. Jangan membaca `game_id_private` dari profil lawan; hanya `read_shared_game_id` setelah izin eksplisit.
- `user_roles`, laporan, tindakan moderasi tidak dapat ditulis langsung oleh client. `my_report_status()` memproyeksikan status pelapor tanpa deskripsi/bukti; `review_report(p_id,p_status)` mengizinkan transisi `new → reviewing → resolved/dismissed` hanya admin aktif; `submit_appeal(p_action,p_reason)` tersedia bagi subjek akun restricted; `review_appeal(p_id,p_status)` hanya admin aktif. `admin_audit` mencatat perubahan status laporan/banding, tindakan moderasi, dan katalog; tidak bisa dibaca/diubah klien. Katalog seed bisa dibaca guest; `add_catalog_option` hanya admin, perubahan lain lewat SQL Editor/server pemilik database sampai admin API tervalidasi tersedia.

## Batas keamanan sebelum rilis

Migrasi membatasi RLS, privasi ID, blokir, state ajakan/chat dan audit dasar. **Belum** ada rate limit terdistribusi/IP untuk ajakan, chat, laporan, serta Auth; Edge Function atau gateway wajib menambahnya sebelum produksi. Belum ada kebijakan Storage avatar/bukti, Edge Function penghapusan akun, retensi, validasi tipe file/EXIF. Alur banding hanya pencatatan/triase, bukan pemulihan otomatis. Jangan buka upload bukti atau avatar publik tanpa kebijakan teruji. Moderasi pesan bukti harus dibatasi per kasus, bukan akses admin bebas ke chat. Pencarian memakai offset sementara; data berubah antarhalaman dapat menggeser hasil, deduplikasi klien diperlukan hingga cursor keyset diterapkan. Katalog rank awal bersifat contoh, bukan klaim sinkronisasi resmi game. Validasi server `attributes` membatasi key dan ukuran, tetapi tipe/nilai detail masih perlu aturan per game sebelum formulir detail dibuka untuk umum.

## Verifikasi

`node tests/sql/smoke.mjs` telah menjalankan kedua migrasi, seed, dan `tests/sql/mvp.sql` dalam PGlite dengan role `anon`/`authenticated` dan klaim JWT sintetis; hasil lulus. PGlite bukan layanan Supabase. Belum diuji terhadap Auth/PostgREST/Storage/Realtime Supabase terpasang. Sebelum bergantung pada fitur, jalankan tes di proyek development menggunakan `psql` sebagai pemilik database, lalu uji RLS via REST memakai token anon, pemilik, pengguna lain, admin, dan restricted; uji konkurensi dua ajakan berlawanan. Belum layak diklaim siap produksi.
